# Accessibility audit

A dedicated audit pass over a page or flow: measure conformance to WCAG 2.2 AA and produce a ranked findings list. Building accessible components is `references/frontend.md`; remediation hands back to it.

## Automated pass (necessary, not sufficient)

- Run axe-core (`@axe-core/cli`, or `@axe-core/playwright` in an E2E test) on each page and state, then Lighthouse accessibility for a second opinion.
- Tools catch roughly a third of issues. Never stop here: keyboard, focus and screen-reader problems mostly do not show up.

## Manual checklist

- **Keyboard:** every interactive element reachable and operable; logical focus order; visible focus ring; no traps; `Esc` closes overlays.
- **Screen reader:** run VoiceOver or NVDA through the flow. Each control announces name, role and state; landmarks (`main`, `nav`, `header`) exist.
- **Structure:** exactly one `<h1>`, no skipped heading levels, real lists, landmarks over `<div>` soup.
- **Forms:** programmatic `<label>` on every input (a placeholder is not one); errors tied by `aria-describedby` and announced; required state conveyed non-visually.
- **Contrast:** body text 4.5:1, large text 3:1, UI components and graphics 3:1; meaning never by color alone.
- **Media:** meaningful `alt` or `alt=""` for decorative; captions or transcripts for audio and video.
- **Dynamic content:** async updates via `aria-live`; modals trap focus and return it to the trigger; `prefers-reduced-motion` respected.
- **Zoom and reflow:** 200% zoom loses nothing; at 320px width no horizontal scroll.
- **Target size (2.2):** interactive targets at least 24x24 CSS px, or adequately spaced.

## Static review (diff only, no browser)

With no axe, Lighthouse or screen reader, check what markup and styles reveal and say plainly that this is a static pass, not a substitute for the passes above:

- Semantic elements and ARIA are present and correctly paired (a `role="button"` div also needs a key handler and `tabindex`).
- Each control's label wraps it or matches its `for` and `id`.
- Interactive elements are real buttons, links and inputs, not `<div onClick>`.
- Color tokens meet the design system's own contrast pairs where the values are visible in the diff.
- `alt` text is present and is not the filename.

## Reporting

Rank by user impact:

- **Blocker:** an assistive-tech user cannot complete the task (unlabeled submit, keyboard trap, invisible focus).
- **Serious:** a major barrier with a workaround (poor contrast on key text, missing headings).
- **Moderate or Minor:** friction and best-practice gaps.

Each finding gives the WCAG success criterion (for example 1.4.3, 2.4.7, 2.5.8), the location (page and element or selector), the user impact and the specific fix. The real findings come from the manual pass with an actual screen reader.
